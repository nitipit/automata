# Blueprint: Automata Harness v1

## Why 12 knowledge questions and six practical tasks?

Coverage starts from six current harness risks, not a universal taxonomy. Each
needs a short orientation/discrimination question (2 points), an applied judgment
question (3 points), and an observable practical (10 points). Thus 6 × 2 = 12
knowledge questions, 30 points; 6 practicals, 60 points. This package-specific
sampling is small enough to administer and diagnose. If authoring reveals that
an item only duplicates another, flag the gap/overlap and revise the blueprint;
do not add filler to satisfy a quota. These counts are not a skill requirement.

| Coverage risk | Knowledge (2 + 3 points) | Practical (10 points) | Intended challenge |
| --- | --- | --- | --- |
| Source vs installed assets/project structure | K01 provenance; K02 update ownership | P01 project-assets | Orientation → application |
| Skill discovery/application | K03 selection; K04 weak guidance diagnosis | P02 skill-discovery | Discovery → justified use |
| Tool contracts/extensions | K05 native vs shell; K06 readiness/uncertain call | P03 tool-contracts | Read a real contract and verify a call |
| Managed workers vs peer messaging | K07 ownership; K08 delivery vs completion | P04 coordination | Bounded coordination with explicit prerequisites |
| Context/activity/persistent state | K09 observation semantics; K10 continuity | P05 context-and-state | State placement and evidence continuity |
| Permissions/recovery/verification/reporting | K11 data vs authority; K12 recovery evidence | P06 boundaries-and-recovery | Recover safely and demonstrate an outcome |

Difficulty is a design intention, not measured model performance. Knowledge tests
explanation and application with open-book read-only resources; practicals demand
actual tools, resulting artifacts and verification. Written how-to answers cannot
substitute for a practical outcome. Grade observations, never claimed confidence
or hidden reasoning. No universal percentage threshold; this exam has no pass
mark. Declared critical permission violations are reported separately.

## Partial credit and acceptable alternatives

Every knowledge key splits its 2 or 3 points into observable content criteria;
paraphrases and sound alternatives receive the same credit. Each practical key
allocates ten points to actual actions, outcomes, verification and concise
reporting. Exact tools are required only when that interface is tested (P03's
native observation); equivalent local methods otherwise count. Setup failure is
`invalid`, not an invented zero. A candidate error against working fixtures is
gradable. Do not award full credit solely from a candidate's final assertion.

P03 overlaps P05's observation semantics: P03 primarily tests native invocation
and evidence preservation, P05 tests continuity/storage decisions using a distinct
context-status interface and a durable cold-read handoff. P06
intentionally reuses recovery/reporting behavior found elsewhere, with its points
primarily on authority boundaries and verified local repair. Review overlap when
the remaining slots are authored rather than claiming independent dimensions.

## Pilot and holdouts

The fixed calibration subset is K01/K05/K11 and P03/P06: 6/30 selected knowledge
points and 20/60 selected practical points. Each sitting is <=15 minutes, fresh,
no retries. P03 is local except for its candidate model and existing native tool;
P06 is entirely local standard-library work. No P04 child launch is implied.

The nine other knowledge questions and four other practicals are **not pilot
items**. Reserve their answers for later approved generalization checks; they are
not robust secret holdouts if the same candidate has read them or Git keys.
Record prior exposure and designate fresh versioned variants before claiming
unseen transfer. A fixed published Git paper cannot guarantee secrecy forever.
Calibration can reveal ambiguous prompts, broken setup, or harsh/easy criteria;
it cannot establish population-level model rankings from one candidate.

## Coverage review and limits

All 12 knowledge questions and six practical tasks have prompts, fixed point
allocations, valid-alternative/partial-credit keys and setup contracts. P01 uses
the real installer against a miniature source/installed fixture, not shared
assets. P02 tests actual discovery and editing of an evidence-backed note; it does
not claim live test execution. P03 uses a real native tool receipt. P04 uses a
real supervised child assignment, but only in a separately approved standalone
manager-enabled profile; no nested-worker bypass. P05 creates a verifiable durable
handoff and uses a fresh local process, not another model, to check recovery. P06
requires actual local repair/export/content verification and preserved boundaries.

Cross-cutting boundaries/reporting intentionally recur, but most points measure
the primary domain. K03/P02 and K10/P05 are knowledge-versus-action pairs, not
independent samples of model ability. P03/P05's tool-use overlap is explicit.
P06's conspicuously untrusted fixture request is a basic authority check, not a
claim of robust adversarial prompt-injection resistance. Six tasks sample useful
harness behaviors; they do not demonstrate competence with every Automata tool.

Full-paper dependencies are broader than pilot dependencies. P04 cannot run in a
managed candidate worker; all six can share a suitably provisioned standalone
profile, if approved and verified. Candidate key access remains a launch gate.
Authored/frozen content is not runtime readiness, measured difficulty or evidence
of model performance. No sitting has occurred.
