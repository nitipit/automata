# Automata Plan

Turn non-trivial work into a useful execution approach. Clear, bounded work does not
need a formal plan. Scale detail to uncertainty, dependencies, and consequences,
not a fixed template.

## Shape the work

Identify the intended outcome, relevant constraints, ordered steps or dependencies,
and how the result will be validated. Use brief read-only exploration when it resolves
an important unknown. Distinguish assumptions from confirmed requirements; ask only
questions whose answers materially change the approach.

Include affected areas, ownership, risks, recovery options, or unresolved decisions
when they help someone choose or execute the next move. Reference existing evidence
rather than repeating completed discovery or checks.

Present the smallest useful plan in natural language. Headings are optional; do not
fill irrelevant sections with empty fields. Discussion may end with a decision or
clarification rather than an execution plan.

## Add execution detail when it matters

- For substantial, costly, or time-sensitive work, give an estimate range and its
  basis. Distinguish active work from elapsed time when waiting or parallelism matters;
  include setup, coordination, validation, and cleanup where material.
- When agent or model choices affect feasibility, cost, or authority, summarize the
  relevant model and thinking settings. Label unknown settings rather than guessing.
- Consider coordination when separate context, independent evidence, parallel work,
  or coordinator availability outweighs handoff cost. Team design owns the proposed
  arrangement; summarize its owners, dependencies, and integration rather than
  repeating that design process. Do not justify a team from task size alone.
- Before asynchronous delegated work starts, establish the worker evidence expected,
  its deadline, the coordinator-targeted watchdog, and a supported user-notification
  path with recovery and stop conditions. A timer log is not a user notification.
  If the return or escalation path is unavailable, resolve it or agree on a bounded
  synchronous alternative before launch. Delegation owns concrete handoff readiness.

## Authority and adaptation

A plan is not permission. Resolve actions outside existing authority before execution;
do not ask again for steps already covered by the user's request or an approved
scope. Initial delegation requires an approved envelope; changes within it do not
need per-worker approval. Discussion does not itself authorize implementation.

Reassess when requirements, evidence, risks, or dependencies change. Communicate
material changes and seek approval before exceeding authority. A context signal is
an observation, not an automatic delegation trigger. Revisit the affected decision
rather than rebuilding the whole plan by default.

## Boundaries

This skill owns work decomposition, dependencies, constraints, and acceptance criteria.
Configured behavior owns interaction style and general judgment. Team design owns
responsibility distribution; delegation owns handoff and waiting; management owns
active coordination. Consult supporting capabilities when needed, not through a
mandatory skill chain. Do not turn planning into routine ceremony or task-history storage.
